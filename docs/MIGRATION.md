# Переезд на другой хостинг

blesk не привязан к хостеру. Всё, что нужно для работы сервера, каждую ночь уходит в зашифрованном виде к другому провайдеру, а приложения ходят на сервер по домену. Переезд — это новый сервер, одна кнопка в GitHub и смена одной DNS-записи.

## Что где лежит

| Что | Где | Кто может прочитать |
|---|---|---|
| Основной сервер | Aeza, Москва, `blesk-msk` | хостер видит только зашифрованное |
| Резервные копии | S3 у другого провайдера (не Aeza) | никто без пароля копий |
| Пароль копий | секрет `BACKUP_PASSWORD` в GitHub и у владельца офлайн | владелец |
| Домен и DNS | у регистратора домена (не Aeza) | — |
| Ключ входа на сервер | секрет `VPS_SSH_KEY` в GitHub | GitHub Actions |

Копия — снимок restic: дамп PostgreSQL (снят на ходу, целостный), файлы MinIO (вложения, они и так зашифрованы на телефонах), `deploy/.env` (пароли базы, MinIO, LiveKit) и `deploy/certs`. restic шифрует всё на сервере до отправки, хранилище видит только непрозрачные блоки.

- Когда: каждую ночь в 03:30 по Москве (таймер `blesk-backup.timer`), сразу после установки и после переезда.
- Сколько хранится: 7 ежедневных, 4 еженедельных и 6 ежемесячных снимков.
- Проверка: по воскресеньям сервер читает обратно десятую часть копии; GitHub каждый день проверяет, что свежий снимок не старше 36 часов, а по понедельникам целиком восстанавливает его на своей машине и запускает на нём сервер (`Actions → Backup check`). Красная проверка приходит владельцу письмом.

Цели: потеря данных — не больше суток (RPO 24 ч), время переезда — около часа (RTO 1 ч), из них большая часть — покупка сервера и обновление DNS.

## Переезд по шагам

Подходит и для плановой смены хостера, и для аварии, когда старого сервера уже нет.

1. Купить новый VPS у любого хостера: Ubuntu 24.04, x86_64, не меньше 2 ГБ памяти. Дать ключу GitHub доступ на него: публичная часть ключа (`ssh-ed25519 …`) записана в итоге любого запуска **Deploy server** в GitHub. Её либо вставляют в панели хостера при покупке («SSH-ключ»), либо добавляют в Termius, зайдя по паролю от хостера: `mkdir -p ~/.ssh && echo 'ssh-ed25519 …' >> ~/.ssh/authorized_keys`.
2. Если старый сервер жив — остановить его, чтобы он не успел принять сообщения после последней копии: `cd /opt/blesk/deploy && docker compose stop server && /opt/blesk/scripts/backup.sh`. Последняя копия при этом свежая, потерь нет.
3. GitHub → Actions → **Deploy server** → Run workflow: `host` — IP нового сервера, `domain` — текущий домен, галочка **restore**. Скрипт поставит сервер, вернёт пароли, сертификат, вложения и базу из последнего снимка, запустит всё и сразу сделает первую копию уже с нового сервера.
4. У регистратора домена поменять A-запись домена на IP нового сервера. TTL заранее стоит 300 секунд, поэтому приложения переходят за несколько минут сами, без нового QR.
5. В секрете `VPS_HOST` заменить IP на новый.
6. Проверить: `https://<домен>/v1/info` отвечает, на телефоне приходят сообщения, `Actions → Backup check` зелёный.
7. Старый сервер выключить и удалить у хостера, когда новый проработал сутки.

Без домена приложения знают сервер по IP и отпечатку сертификата: после переезда IP другой, сертификат выпускается новый, и всем придётся заново сканировать QR. Поэтому основной сервер работает только по домену.

## Что не переносится

- Подписки на push-уведомления и активные сессии звонков — телефоны переподключатся сами.
- Сообщения, принятые сервером после последней копии, если старый сервер пропал внезапно (не больше суток). Сообщения, ещё лежавшие в очереди отправителя на телефоне, дойдут после переподключения.

## Учения

Сценарий 93: раз в квартал владелец нажимает `Actions → Backup check → Run workflow` и смотрит итог: «Snapshot … restored: N accounts, M attachments». Это полный переезд на машину GitHub, только без смены DNS. Проверено на тестовом стенде при подготовке плана: бэкап → удаление сервера вместе с томами → восстановление на другой машине; аккаунты и вложения вернулись, с неверным паролем копия не открывается, поверх живого сервера восстановление отказывается работать.
