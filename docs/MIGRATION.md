# Переезд на другой хостинг

blesk не привязан к хостеру. Всё, что нужно для работы сервера, может каждую ночь уходить в зашифрованном виде к другому провайдеру, а приложения ходят на сервер по домену. Переезд — это новый сервер, одна кнопка в GitHub и смена одной DNS-записи.

**Сейчас это не включено.** Копий нет, пока владелец не завёл хранилище у другого провайдера и не добавил секреты `BACKUP_*` (`NEEDS_HUMAN.md`, 2.7); до этого `Actions → Backup check` красный. Кнопки **Deploy server** и **Backup check** появляются в GitHub только после того, как рабочая ветка станет основной (`NEEDS_HUMAN.md`, 2.4). Всё ниже описывает, как это работает после этих двух шагов.

## Что где лежит

| Что | Где | Кто может прочитать |
|---|---|---|
| Основной сервер | Aeza, Москва, `blesk-msk` | хостер видит только зашифрованное |
| Резервные копии | S3 у другого провайдера (не Aeza) | никто без пароля копий |
| Пароль копий | секрет `BACKUP_PASSWORD` в GitHub и у владельца офлайн | владелец |
| Домен и DNS | blesk.su у Aeza (позже — к отдельному регистратору) | — |
| Ключи входа на сервер | `VPS_SSH_KEY` (пользователь `deploy`) в GitHub; ключ владельца `~/.ssh/blesk_owner` на ноутбуке | GitHub Actions; владелец |

Копия — снимок restic: дамп PostgreSQL (снят на ходу, целостный), том `attachments` (вложения, они и так зашифрованы на телефонах), `deploy/.env` (пароли базы и LiveKit) и `deploy/certs`. restic шифрует всё на сервере до отправки, хранилище видит только непрозрачные блоки.

- Когда: каждую ночь в 03:30 по Москве (таймер `blesk-backup.timer`), сразу после установки и после переезда.
- Сколько хранится: 7 ежедневных, 4 еженедельных и 6 ежемесячных снимков.
- Проверка: по воскресеньям сервер читает обратно десятую часть копии; GitHub каждый день проверяет, что свежий снимок не старше 36 часов, а по понедельникам целиком восстанавливает его на своей машине и запускает на нём сервер (`Actions → Backup check`). Красная проверка приходит владельцу письмом.

Цели: потеря данных — не больше суток (RPO 24 ч), время переезда — около часа (RTO 1 ч), из них большая часть — покупка сервера и обновление DNS.

## Переезд по шагам

Подходит и для плановой смены хостера, и для аварии, когда старого сервера уже нет.

1. Купить новый VPS у любого хостера: Ubuntu 24.04, x86_64, не меньше 2 ГБ памяти. На ноутбуке владельца запустить `server-setup` с адресом нового сервера (Windows: `$env:BLESK_SERVER='<IP>'; powershell -ExecutionPolicy Bypass -File scripts\owner\server-setup.ps1`, macOS: `BLESK_SERVER=<IP> bash scripts/owner/server-setup.sh`) — он один раз спросит пароль root от хостера, поставит ключ владельца и пользователя `deploy` с ключом GitHub и покажет новый ключ сервера. Сразу заменить в GitHub секреты `VPS_HOST` (новый IP) и `VPS_KNOWN_HOSTS` (новый ключ сервера): без них GitHub к новому серверу не подключится.
2. Если старый сервер жив — остановить его, чтобы он не успел принять сообщения после последней копии: `cd /opt/blesk/deploy && docker compose stop server && /opt/blesk/scripts/backup.sh`. Последняя копия при этом свежая, потерь нет.
3. В DNS домена (сейчас — панель Aeza) поменять A-записи `@`, `www` и `api` на IP нового сервера. TTL заранее стоит 300 секунд, поэтому приложения переходят за несколько минут сами, без нового QR. Сертификаты на новом сервере выпускаются, только когда домен уже указывает на него, поэтому DNS меняется до установки.
4. GitHub → Actions → **Deploy server** → Run workflow: `domain` — `api.blesk.su`, `site_domain` — `blesk.su`, галочка **restore**. Скрипт поставит сервер, вернёт пароли, сертификат, вложения и базу из последнего снимка, запустит всё и сразу сделает первую копию уже с нового сервера.
5. Проверить: `https://api.blesk.su/health` отвечает `{"status":"ok"}`, сайт blesk.su открывается, на телефоне приходят сообщения, `Actions → Backup check` зелёный.
6. Старый сервер выключить и удалить у хостера, когда новый проработал сутки.

Без домена приложения знают сервер по IP и отпечатку сертификата: после переезда IP другой, сертификат выпускается новый, и всем придётся заново сканировать QR. Поэтому основной сервер работает только по домену.

## Что не переносится

- Подписки на push-уведомления и активные сессии звонков — телефоны переподключатся сами.
- Сообщения, принятые сервером после последней копии, если старый сервер пропал внезапно (не больше суток). Сообщения, ещё лежавшие в очереди отправителя на телефоне, дойдут после переподключения.

## Учения

Сценарий 93: раз в квартал владелец нажимает `Actions → Backup check → Run workflow` и смотрит итог: «Snapshot … restored: N accounts, M attachments». Это полный переезд на машину GitHub, только без смены DNS.

Что проверено: на тестовом стенде с MinIO вместо S3 (16.10 и 22.10.2026) — бэкап → удаление сервера вместе с томами → восстановление на другой машине; аккаунты и вложения вернулись, с неверным паролем копия не открывается, поверх живого сервера восстановление отказывается работать; `restore-drill.sh` поднимает сервер из копии и считает аккаунты. С настоящим сервером и настоящим хранилищем — ещё нет: копий пока нет.
